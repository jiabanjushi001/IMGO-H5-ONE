# IMGO 容量测试

只在独立测试环境执行。压测机与服务端分开部署，配置、数据规模、TLS/Nginx/MySQL设置尽量接近生产；经 Cloudflare 测量的是完整链路容量，需要与源站瓶颈区分。当前没有实测容量结论。

## 准备

需要测试 API/WS 地址、服务器 CPU/内存/带宽、数据库部署位置、SSH 访问方式，以及允许创建专用账号和群。不要使用真实用户 Token。每个模拟用户使用独立账号（工具会检查身份，不能用一个 Token 建立大量连接冒充多用户）。所有发消息的测试用户必须已加入指定测试群。

工具不会自动创建、删除数据，也不修改服务端限流。发送测试会落库，可能更新未读计数和触发现有通知，只能选用专用账号和测试群。不要使用真实群。

构建：

```sh
go build -o bin/imgo-loadtest ./cmd/imgo-loadtest
```

Token 文件 `tokens.json` 格式（保存为仅本人可读，例如 chmod 600）：

```json
[{"token":"TEST_USER_1_TOKEN"},{"token":"TEST_USER_2_TOKEN"}]
```

默认只检查本地参数，不发任何请求。增加 `-execute` 才实际连接。

```sh
./bin/imgo-loadtest -base https://TEST-API.example -tokens tokens.json -users 10 -duration 1m
```

## 逐级测试

1. 冒烟：10 个账号，只在线 1 分钟，验证鉴权与心跳。
2. 只在线：100、300、500、1000 人等逐级增加，探索阶段可先短测，再对候选容量稳定观察至少 5 分钟。上一档无明显错误且服务器有余量再提升。
3. 群聊：独立测 20、100、500 人群，逐级增加全群总发送速率，如 1、5、10、20 条/秒。
4. 多群：不同进程使用互不重复的账号文件和不同群；各进程接收者应覆盖所在测试群。
5. 找到临界点后重复测并做长时间稳定性测试，再根据业务峰值与资源波动保留余量。

例如 100 人群、全群 5 条/秒、持续 5 分钟：

```sh
./bin/imgo-loadtest -base https://TEST-API.example -tokens tokens.json \
  -users 100 -ramp 200ms -group group-5 -rate 5 -duration 5m -execute
```

每条消息推送到这 100 个在线测试用户（含发送者），理论接收量约 500 次/秒。这里 5 是全群速率，并非每人 5 条/秒。工具轮流选择发送者；高发送间隔配置可能导致业务限流，需要把该结果与容量故障区分。

建连准备最多同时进行16个身份/群权限/握手流程，`-ramp` 控制启动间隔。每个连接都必须完成Token绑定后才计为在线。

## 结果解释

- `online_end`：已成功鉴权绑定且连接仍在的测试用户数。
- `disconnects`：测试期间意外断线数。
- `errors`：按错误类型归类的失败次数。
- `started_at`：稳定阶段开始时间（UTC），用于与服务器监控对齐。
- `attempted/accepted/failed`：HTTP 发消息请求数、业务成功数、失败数。
- `api_p95_ms`：HTTP请求耗时P95，包括失败请求。
- `delivery_p95_ms/delivery_p99_ms`：从请求开始到收到WS消息的耗时，仅统计业务成功且已收到的消息。
- `expected_deliveries/received_deliveries`：成功发送数×测试人数，与去重后的实际送达数。结束时留5秒接收；缺失可能是超时、断线或未送达，不能仅凭低延迟忽略它。
- `generator_skipped`：压测机的32个并发发送槽位已满，未达到目标发送速率；该轮不能声称完成了目标负载。

收到中断信号会停止。稳定阶段每5秒检查，发生断线，或至少尝试20条后失败占比超过5%，停止继续加压。连接/鉴权预检失败则不进入发消息阶段。单轮最多100000条消息、2000000次预计送达，防止统计器占用过大；大规模时缩短单轮或拆分压测机。工具使用真实API和TLS校验，不输出Token。

建议预先确定合格指标，例如错误率<0.1%、无意外断线、送达率>=99.9%、群消息P95<500ms，并结合实际网络与业务要求调整。这些是建议门槛，不是本项目已达到的性能承诺。

## 服务端同步观察

记录每一档测试起止时间：CPU、RSS内存、网络进出流量、文件描述符数、MySQL连接数/慢查询/锁等待、磁盘延迟；同时观察压测机自身CPU和带宽。可用现有监控或 `top`、`vmstat 1`、`iostat -xz 1`、`ss -s`。缺少监控时先补齐，不通过关限流或改鉴权得到虚高结果。

当前代码有群消息数据库写入/全群未读更新、在线成员推送、定时会话校验等开销；必须带入群规模和消息速率测试。单纯建立空连接不能代表聊天容量。
