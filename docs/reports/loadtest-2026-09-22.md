# IMGO 容量实测报告 — 2026-09-22

## 结论

**当前2 vCPU、约4 GB内存的服务器，在本次源站测试链路中，1000个独立用户同群在线、全群合计每秒10条文本消息通过短测，并通过相同双隧道链路复核。每秒20条同群消息出现CPU满载、严重实时推送积压和断线，未通过。**

这是已验证的场景边界，不能解释为“最多只能在线1000人”，也不能保证真实公网长期稳定支持1000人。测试未覆盖超过1000人的闲置连接上限、多群不同分布、图片/视频、历史记录读取、前端渲染或长时间稳定性。每秒消息数是全群合计，不是每个用户的发送速率。

## 服务器和测量方法

- 目标：66.42.53.148；API https://imgo.myad.top，WebSocket wss://imgo.myad.top/wss。用户确认独立测试环境并授权创建测试数据。
- CPU：2 vCPU，AMD EPYC-Rome；内存3.8 GiB，约4 GB；MySQL与IMGO同机，宝塔和其他进程同时运行。套餐带宽未提供。
- 测试前整机CPU约51%，IMGO本身接近空闲；此既有负载包含在测试CPU指标中，未停止其他服务。
- 运行中的服务SHA256：`2daea436cd5831377fdecc7c51032dbf73e2ffbeb954d1174c0f2331578f3ac8`。测试期间未部署新服务二进制。
- 压测程序运行在Mac，通过SSH隧道访问服务器127.0.0.1:8088。后续将HTTP和WS分成独立隧道。SSH开销计入服务器CPU与网络数据，因此不等同于生产Nginx/Cloudflare路径。
- 每个模拟用户均为独立普通用户，经过真实登录、Token身份预检、群成员检查与WebSocket绑定。消息经现有HTTP接口写入数据库，推送经WebSocket接收并按消息ID/接收者去重。
- 群成员均在线，包含发送者；预计接收数=业务成功消息数×在线测试人数。每轮结束留5秒收尾。P95/P99仅计算已收到的成功消息，必须结合送达数量一起解释。
- 保留系统配置：群人数上限0（不限），单用户发送间隔1秒；未为压测关闭限流。

|---|---:|---:|---:|---:|---:|---:|
| 10人，1条/秒，60秒 | 59 | 590 / 590 | 0 | 73 ms | 53.2% / 61.2% | 71.5 MB |
| 100人，5条/秒，90秒 | 449 | 44,900 / 44,900 | 0 | 71 ms | 56.8% / 61.8% | 69.9 MB |
| 500人，10条/秒，90秒 | 900 | 450,000 / 450,000 | 0 | 129 ms | 72.7% / 76.4% | 89.4 MB |
| 1000人，10条/秒，120秒 | 1,199 | 1,199,000 / 1,199,000 | 0 | 150 ms | 85.6% / 89.1% | 125.8 MB |

500人/10条每秒：出口峰值约52.8 Mbps；1000人/10条每秒：出口峰值约109.1 Mbps。内存余量仍较大，当前高负载下首先表现出来的是CPU和实时传输压力，而非内存容量耗尽。网络统计为整机接口流量，包含SSH和其他服务。CPU资源每2秒采样，表中平均包含5秒收尾；饱和测试后半段流量下降，因此不能只看全轮平均CPU。

### 每秒20条为何不合格

- 双隧道复测中，999次发送接口均返回成功，但999000次预计接收中，在统计窗口内只收到41679次（约4.17%），163个连接断开。
- 已送达部分的P95约51.21秒、P99约52.28秒。不能用“接口成功率100%”代表聊天服务正常。未在统计窗口收到的消息不等于数据库永久丢失，本次测的是实时送达。
- CPU采样多次达100%，进程RSS峰值270.1 MB，出现积压后自动停止继续发消息。
- 该失败说明当前测试路径在此负载下不合格；尚未单独分离Go、数据库和SSH传输各自的瓶颈，不能将其作为Go后端的绝对吞吐上限。

## 排除的测试与公网限制

- 首次10人试跑发生SSH控制连接退出，后续低负载复测成功；这次失败不用于判断服务容量。
- 首次1000人/20条每秒触发单条SSH通道附近的错误，日志出现 `channel ... open failed` 和 `poll: Invalid argument`，1000连接同时断开。该轮已排除，随后改为两条独立隧道重测。
- Mac请求公网域名出现间歇性HTTP传输超时：单次公开接口也曾15秒无响应，后续单次GET恢复200，但100人公网预检再次失败。公网路径尚未完成有效容量测试。不能据本报告承诺当前公网API/WSS表现。

## 实际使用建议

- 已实测通过1000人同群、每秒10条文本消息，但整机CPU平均约86%，余量有限。若采用本次大群消息模型，可先按500人档作为更保守的规划起点，再用真实流量分布做长时间验证；这不是对所有群规模通用的用户上限。
- 上线前优先查清测试前已有的约51%CPU占用，并完成公网链路排查。之后在相同配置的独立环境完成至少5分钟候选负载复测及更长稳定性测试。
- 多个小群与一个千人大群的广播次数不同，不能只按在线人数推算吞吐。视频文件等流量需另测。

## 测试结束状态与数据

- 已停止压测发消息和专用资源采样。源站公开API复查返回HTTP 200，CPU恢复约51–52%基线，IMGO进程仍为原进程，没有重启。
- 保留1000个专用测试账号，账号前缀 `lt1790007172_`；测试群分别为group-18、group-19、group-20、group-21。未执行批量删除。
